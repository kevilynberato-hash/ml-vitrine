O que o modelo resolve

Racional (baseado no bench com Yuri Laranja)

Sem checkpoints fixos

Nada de "no D3 decide X, no D5 decide Y". Todo dia o modelo analisa cada parceiro e recalcula a probabilidade. O parceiro pode ficar 1 dia, 3 dias ou 7 dias — depende do comportamento dele, não de uma regra rígida.

Modelo único com dia como feature

Em vez de um modelo por checkpoint, um modelo só com dia_observacao como feature. O modelo aprende sozinho que D1 tem peso diferente de D5, e que 3 dias de estagnação no D4 é pior que no D2.

Inferência diária para todos os ativos

Todo dia o script pega todos os parceiros que ainda estão na janela de 7 dias e não converteram, recalcula as features acumuladas até aquele dia e roda o modelo salvo.

Ausência de engajamento é dado

Parceiro que não interage, não faz setup, não abre o app → isso é o sinal mais forte de que ele precisa de ajuda do comercial. O modelo aprende esse padrão.

Arquitetura — Modelo Único (sem checkpoints fixos)

Por que um modelo só?

Em vez de treinar um modelo para D1, outro para D3, outro para D5, D7... treinamos um modelo único onde dia_observacao é uma feature. O XGBoost aprende automaticamente as interações: "3 dias de estagnação no D4 é pior que 3 dias no D2", "setup 50% no D1 é ótimo, no D7 é alarmante".

Isso também resolve o problema de dados: se treinássemos modelos separados, o modelo D7 só veria parceiros que chegaram ao D7 (viés de sobrevivência). Com um modelo único, todos os snapshots de todos os dias entram no treino.

Algoritmo: XGBoost

  • 81 features (todas as listadas na aba Features)
  • Target: target_5pdd_30d (11% positivo)
  • scale_pos_weight: ~8 (89/11)
  • Treino: Abr-Mai/26 · Teste: Jun/26
  • Validação: temporal (não aleatória) — sem data leakage

Como o modelo decide (inferência diária)

1. Todo dia às 7h

Script busca todos os parceiros com ganho entre D1 e D7 que ainda não fizeram 5pdd. Para cada um, calcula as features acumuladas até aquele dia (D0→hoje).

2. Modelo carregado da sandbox

O modelo já foi treinado e serializado. O script diário NÃO retreina — só carrega o .pkl e faz model.predict_proba().

3. Score + Flag

Para cada parceiro: prob_ativar_sozinho (0→1). Se prob < threshold (ex: 0.30) → precisa_comercial = 1. Senão, continua em Self e será reavaliado amanhã.

Threshold — como calibrar

Threshold% transbordadosPerfilQuando usar
20%~35%Agressivo — deixa mais SelfYuri usa esse. Time comercial enxuto, alta confiança no Self.

Query 2: Treino do Modelo (Python — Databricks)

# Executar UMA VEZ. Salva modelo em sandbox.
import pandas as pd
import xgboost as xgb
from sklearn.model_selection import train_test_split
import pickle

# 1. Carregar base de treino
df = spark.table("default.ml_vitrine_treino_snapshots").toPandas()

# 2. Separar features e target
target_col = "target_5pdd_30d"
id_cols = ["merchant_id", "crmdb_id", "deal_id", "merchant_name",
           "dt_ganho", "dia_observacao", "data_snapshot"]
target_cols = ["target_1pdd_7d", "target_delivery_5pdd_30d",
               "target_salao_5pdd_30d", "dias_ate_1pdd",
               "dias_ate_5pdd_del", "dias_ate_5pdd_sal"]
feature_cols = [c for c in df.columns
                if c not in id_cols + target_cols + ["target_5pdd_30d"]]

# 3. Split temporal (treino Abr-Mai, teste Jun)
df['mes'] = pd.to_datetime(df['dt_ganho']).dt.month
train = df[df['mes'].isin([4, 5])]
test  = df[df['mes'] == 6]

# 4. Treinar XGBoost (modelo UNICO — dia_observacao como feature)
scale = (train[target_col] == 0).sum() / (train[target_col] == 1).sum()
model = xgb.XGBClassifier(
    scale_pos_weight=scale,
    max_depth=6,
    learning_rate=0.05,
    n_estimators=200,
    eval_metric='auc'
)
model.fit(train[feature_cols], train[target_col])

# 5. Avaliar
from sklearn.metrics import roc_auc_score
prob = model.predict_proba(test[feature_cols])[:, 1]
print(f"AUC: {roc_auc_score(test[target_col], prob):.3f}")

# 6. Serializar em sandbox
with open("/dbfs/mnt/sandbox/ml_vitrine_model.pkl", "wb") as f:
    pickle.dump({"model": model, "features": feature_cols}, f)

# Script diario — Databricks Workflow, agenda 7h
import pandas as pd
import pickle

# 1. Carregar modelo serializado
with open("/dbfs/mnt/sandbox/ml_vitrine_model.pkl", "rb") as f:
    saved = pickle.load(f)
model = saved["model"]
feature_cols = saved["features"]

# 2. Features dos parceiros ativos (ultimos 7 dias, sem 5pdd)
df_ativos = spark.sql("""
  SELECT * FROM default.ml_vitrine_treino_snapshots
  WHERE dt_ganho >= DATE_ADD(CURRENT_DATE(), -7)
    AND target_5pdd_30d IS NULL  -- ainda nao ativou (em producao)
""").toPandas()

# 3. Inferencia
df_ativos["score_ativar_sozinho"] = model.predict_proba(
    df_ativos[feature_cols]
)[:, 1]

THRESHOLD = 0.30  -- calibrar com backtest
df_ativos["precisa_comercial"] = (
    df_ativos["score_ativar_sozinho"] < THRESHOLD
).astype(int)

# 4. Regra dos 7 dias: transborda automatico
df_ativos.loc[
    df_ativos["dia_observacao"] >= 7,
    "precisa_comercial"
] = 1

# 5. Salvar tabela de output
output = df_ativos[[
    "merchant_id", "merchant_name", "dia_observacao",
    "score_ativar_sozinho", "precisa_comercial"
]]
spark.createDataFrame(output).write.mode("overwrite")\
    .saveAsTable("default.ml_vitrine_score_diario")

  3. Retreinar mensalmente com dados novos

Passo 3 — Criar Workflow diário

  1. Databricks Workflows → New Job
  2. Schedule: cron 0 7 * * * (7h todo dia)
  3. Task: notebook com script de inferência (Query 3)
  4. Output: tabela ml_vitrine_score_diario

Passo 4 — Integrar com Salesforce

  1. Time de produto lê ml_vitrine_score_diario
  2. Filtra precisa_comercial = 1
  3. Envia flag via API para Salesforce (campo no objeto do restaurante)
  4. No Salesforce, roteador usa a flag para alocar

Teste A/B

  1. Grupo controle (80%): regra atual (48h após último setup)
  2. Grupo teste (20%): decisão do modelo (score diário + threshold 30%)
  3. Métricas: taxa de 1pdd D7, taxa de 5pdd 30d, share Self, conversão global
  4. Duração: 2-4 semanas para ter significância estatística
  5. Se positivo: expandir para 50% → 100%
